Mutexes

A mutex is a lock built for one job: making sure only one task at a time is inside a critical section. Its ownership rule is what separates it from a binary semaphore, and it is what makes priority inheritance possible.

Learning objectives
  • Define a critical section and a mutex.
  • Explain mutex ownership and the three properties it enables: owner-only unlock, recursive locking, and priority inheritance.
  • Choose between a mutex, interrupt masking, a scheduler lock and atomic operations for a given critical section.
  • Size a critical section correctly: protect the whole invariant, nothing more.
  • Explain why a mutex cannot be used from an ISR or for signalling.

The concept

Critical section: a sequence of code that accesses a shared resource and must not be executed by more than one task at a time for the resource to stay consistent.

Mutex (mutual exclusion lock): a kernel object with two states, unlocked and locked, and an owner.

  • lock: if unlocked, it becomes locked and the caller becomes its owner. If locked by another task, the caller blocks (optionally with a timeout).
  • unlock: only the owner may unlock. If tasks are waiting, ownership passes to one of them (normally the highest-priority one), which becomes Ready; otherwise the mutex becomes unlocked.

Every access to the shared resource is wrapped: lock, access, unlock. Because only one task can own the mutex, only one task can be between its lock and its unlock.

What ownership gives you

  • Owner-only unlock. Another task cannot release the lock by mistake. The kernel rejects it, which turns a silent data-corruption bug into a visible error.
  • Recursive locking (in kernels that support it). The owner may lock again; the kernel keeps a lock count and the mutex is released only when the count returns to zero. This lets a locked function call another function that locks the same mutex. Non-recursive mutexes deadlock or report an error in that case.
  • Priority inheritance. Because the kernel knows who holds the lock, when a higher-priority task blocks on it the kernel temporarily raises the owner to that priority, so medium-priority tasks cannot delay the owner indefinitely. This is the subject of Lesson 11; the demo below already shows it.

Alternatives for mutual exclusion

A mutex is not the only way to make a section exclusive. The right choice depends on who shares the data and how long the section is.

When not to use a mutex

  • In an ISR. An ISR is not a task: it cannot block and cannot be an owner. To share data with an ISR, mask that interrupt briefly or use a lock-free queue.
  • For signalling. "Task A unlocks to tell Task B" breaks the ownership rule. Use a semaphore, notification or event group.
  • Around long or blocking operations when you can avoid it: holding a mutex while waiting for a queue, sleeping or doing slow I/O extends the time every other user waits, and is the first step towards deadlock (Lesson 10).
  • For a single word that an atomic operation can update.

Worked example: a shared I²C bus

Two sensor tasks, one bus

A temperature task and an accelerometer task share one I²C bus. A register read is a transaction: START, device address + write, register address, repeated START, device address + read, N data bytes, STOP. If the accelerometer task preempts the temperature task between its register-address write and its read, the bus sequence interleaves and both reads return garbage.

  • Wrong granularity: lock around each byte. Transactions still interleave between bytes.
  • Wrong scope: one "sensor" mutex held while the task also computes and logs its results. Everyone waits for work that does not touch the bus.
  • Right: one mutex per bus, locked for exactly one complete transaction, released before any processing.

The rule generalises: identify the invariant (here, "a transaction is never interleaved") and hold the lock for exactly the code that could break it.

How it differs from the other primitives

Compared withDifference
Binary semaphoreSame 0/1 state, but a mutex has an owner, rejects unlock by non-owners, can be recursive, supports priority inheritance, and is thread-only. A binary semaphore is for signalling; a mutex is for locking.
Counting semaphoreAllows up to N tasks in; a mutex allows exactly one.
Event group, notification, queueThese pass a signal or data from one context to another. A mutex passes nothing; it only excludes.

Common mistakes

  • Missing unlock on an error path. An early return inside the critical section leaves the mutex locked forever. Use one exit point from locked regions.
  • Check-then-act outside the lock. Reading "is the buffer empty?" under the lock, releasing, then writing under a new lock: the state may change in between. Keep the check and the action in the same critical section.
  • Locking in some paths but not all. A mutex protects nothing if one access skips it. Every access to the shared data must use the same mutex.
  • Locking two mutexes in different orders in different tasks. Classic deadlock (Lesson 10).
  • One giant lock for many unrelated resources. Unrelated tasks block each other and response times grow.
  • Assuming recursion is available or forbidden. Kernels differ; check before relying on either.

What this becomes in Zephyr

Zephyr: struct k_mutex
  • Define with K_MUTEX_DEFINE(name) or k_mutex_init().
  • k_mutex_lock(&m, timeout) returns 0, -EBUSY (with K_NO_WAIT) or -EAGAIN (timeout). k_mutex_unlock() returns -EPERM if the caller is not the owner and -EINVAL if the mutex is not locked.
  • Zephyr mutexes are recursive (lock count) and always use priority inheritance. CONFIG_PRIORITY_CEILING caps how high inheritance may raise a thread (default −127, which in practice means no cap).
  • Not ISR-safe. For data shared with an ISR use k_spinlock (k_spin_lock() / k_spin_unlock()), which on this single-core Cortex-M7 masks interrupts, or irq_lock() / irq_unlock(), or the atomic_t API.
  • k_sched_lock() / k_sched_unlock() implement the scheduler-lock alternative.
